# 운영센터 ↔ 사용자 사이트 연결

2026-10-06 매물 공급과 공공임대 응답 분리 구현, 2026-10-07 사용자 기기 푸시 연결. 고객 조건은 사용자 사이트에 보관한다.

- 운영 자료 확정과 불변 catalog_exports 버전 저장은 같은 D1 batch에서 revision/lastOperation 조건으로 처리한다. 미확정 pending은 내보내지 않는다.
- 확정 직후 사용자 /api/integration/sync를 호출한다. 사용자 서버가 운영센터 /api/integration/catalog에서 아직 받지 않은 버전을 순서대로 읽어 shared_catalog에 보존한다. 실패는 자료를 되돌리거나 삭제하지 않으며 운영센터 연결 설정에서 재시도한다. 사용자 페이지 요청도 최근 확인 후 1분 이상 지나면 다시 확인한다. 별도 자동 수집 일정은 만들지 않는다.
- 플랫폼 서비스 인증과 HMAC-SHA256 요청 서명을 함께 사용한다. 서명은 요청 메서드·대상 origin·경로·쿼리·시각·nonce·본문 해시를 묶는다. 유효 시간 5분, 사용 nonce 재사용 금지, 인증 정보는 Sites 런타임 secret만 사용한다. 상대 주소는 서버 설정으로 고정하며 리다이렉트를 따르지 않는다.
- 사용자 화면은 저장된 버전을 순서대로 반영한다. 사용자별 조건·관심·개별 알림 중지·호칭·읽음 상태를 유지하고 낙관적 잠금으로 동시 저장을 보호한다. 기존 사용자 저장 방식은 보존하며 공유 버전과 마지막 처리 sequence를 추가한다. 사용자별 목록·이력 사본은 아직 남아 있고 1.9MB 한도를 검사한다. 장기 운영에서는 개인 이력을 별도 테이블로 분리해야 한다.
- 구독 사용자는 자료 동기화 후 백그라운드에서 조건을 평가해 알림함과 푸시 대기열에 원자적으로 저장한다. 구독하지 않은 사용자는 사이트 조회 시 알림함을 갱신한다. 이미 처리한 sequence는 재평가하지 않는다. 푸시 허용·해제·현재 기기 테스트는 사용자 `내 조건`에서 설정한다. 처리 예산, 재시도와 공급자 접수/실제 표시 구분은 README의 기기 푸시 절을 참고한다.
- 원문 ID 없는 행은 새 버전의 독립 ID로 구분한다. 최초 기준 파일이 기존 사용자 기준 파일과 같으면 기존 관심 링크를 유지한다. 새로운 파일의 행 번호만으로 동일 매물이라 가정하지 않는다.
- 사용자 GET /api/public-housing에는 revision과 feed.notices만 포함한다. 운영 정보는 서명된 /api/integration/housing을 통해 운영센터에서 조회한다. 기존 updater는 서비스 인증과 X-Mapo-Housing-Update: 1로 /api/public-housing/operations를 읽는다. 이 경로는 브라우저 Origin이나 사용자 신원을 가진 요청을 거절한다. 업데이트·일정 쓰기는 기존 owner-private Sites 경계를 유지한다. 공개 범위를 넓히기 전 별도 updater 인증을 추가해야 한다.
- 공공임대 정기 확인 시각과 공고 저장소는 변경하지 않는다. 운영센터의 일정 표시는 저장된 설정이며 실제 스케줄러 가동 확인을 뜻하지 않는다.

검증: 양쪽 타입 검사·빌드, 로컬 D1 두 개를 사용한 verify-integration.mjs. 실제 운영 데이터에는 테스트 고객이나 변경 가격을 넣지 않는다.
